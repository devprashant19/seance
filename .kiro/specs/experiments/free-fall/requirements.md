# Requirements Document — Experiment: Free-Fall Height ("The Drop of Doom")

## Introduction

Measure the height of a short drop by timing how long the phone's accelerometer reads almost zero. An accelerometer measures proper acceleration: about 9.81 m/s² at rest, about 0 in free fall. This file is the input to hook **H1 (summon-experiment)** — in Phase 5 this experiment is deliberately **generated by H1** from this spec, on camera. Physics reference: `phases/phase-05-poltergeist-lab-mvp/experiments-mvp.md` §2.

## Requirements

### Requirement 1 — Rest baseline

**User Story:** As a student, I want the app to learn what "1 g" looks like for my phone, so that the drop detection works on any phone.

#### Acceptance Criteria

1. WHILE in READY_CHECK, THE SYSTEM SHALL require 0.5 s with the `accelG` magnitude varying by less than 0.5 m/s² before enabling Start.
2. THE SYSTEM SHALL take g_s as the median `accelG` magnitude over the 0.5 s before each drop and normalise the magnitude as r(t) = |a|/g_s.

### Requirement 2 — Free-fall detection

**User Story:** As a student, I want each drop found automatically, so that I don't have to mark times by hand.

#### Acceptance Criteria

1. THE SYSTEM SHALL use raw `accelG` samples (no resampling) for edge timing.
2. THE SYSTEM SHALL treat as a free-fall candidate any run where r < 0.3 for at least 3 consecutive samples and at least 80 ms in total.
3. WHEN a candidate is found, THE SYSTEM SHALL time its start as the last downward crossing of r = 0.5 before the run and its end as the first upward crossing of r = 0.5 after it, both by linear interpolation between samples.
4. IF several candidates exist within one drop, THEN THE SYSTEM SHALL use the longest and report the others as info.
5. IF no candidate exists, THEN THE SYSTEM SHALL tell the user the phone never fell freely.
   **Property:** for a synthetic trace with a free-fall window of duration t ∈ [0.15, 0.45] s at sample rate f ∈ [50, 120] Hz with up to 15% timestamp jitter, the detected t_f is within one median sample interval of t.

### Requirement 3 — Height

**User Story:** As a student, I want the drop height with an honest uncertainty, so that I can compare it with my ruler.

#### Acceptance Criteria

1. WHERE mode is `drop`, THE SYSTEM SHALL compute h = ½ · gRef · t_f².
2. WHERE mode is `toss`, THE SYSTEM SHALL compute h_max = gRef · t_f² / 8.
   **Property:** h is strictly increasing in t_f for t_f > 0.
   **Property:** for a synthetic drop from height h ∈ [0.2, 0.8] m, the recovered h is within its reported uncertainty of the true h in at least 95% of noisy cases.
3. WHEN 2 or more drops are recorded, THE SYSTEM SHALL report the mean height, the standard deviation and the number of drops.

### Requirement 4 — Uncertainty

**User Story:** As a student, I want to know that my phone's sample rate limits the accuracy, so that I understand the instrument.

#### Acceptance Criteria

1. THE SYSTEM SHALL estimate the per-edge timing uncertainty u_edge = max(Δt_s/2, half of the 20%→80% transition duration), with Δt_s the median sample interval, and u(t_f) = √2 · u_edge.
2. THE SYSTEM SHALL report u(h)/h = 2 · u(t_f)/t_f, combined in quadrature with the repeat scatter s/√n when n ≥ 2, stating which term dominates.
   **Property:** u(h) never decreases when Δt_s increases, all else fixed.
3. THE SYSTEM SHALL list the assumptions: air drag neglected, clean release, landing edge at first contact, and the bias direction of a soft landing (h too high) and a slow release (h too low).

### Requirement 5 — Data quality

**User Story:** As a student, I want warnings when the drop wasn't clean, so that I can redo it.

#### Acceptance Criteria

1. IF the free-fall run is shorter than 80 ms, THEN THE SYSTEM SHALL emit a major "too short to time" diagnostic.
2. IF the minimum r during the run exceeds 0.15, THEN THE SYSTEM SHALL emit a minor "not a clean fall" diagnostic.
3. IF the landing edge's 20%→80% rise takes longer than 30 ms, THEN THE SYSTEM SHALL emit a minor "soft landing" diagnostic.
4. IF the median sample rate is below 40 Hz, THEN THE SYSTEM SHALL emit a major diagnostic.
5. THE SYSTEM SHALL pass the result, diagnostics, budget and trace statistics to the Physics Oracle.

### Requirement 6 — Teaching moment and notebook

**User Story:** As a student, I want to understand why the phone reads zero while falling, so that I learn the physics, not just the number.

#### Acceptance Criteria

1. WHEN a result is shown, THE SYSTEM SHALL explain in one plain sentence that an accelerometer measures proper acceleration, which is near zero in free fall, like an astronaut in orbit.
2. THE SYSTEM SHALL provide a `notebook.md` template with Aim, Apparatus, Theory, Method (including safety), Data, Calculations, Uncertainty, Result, Assumptions and Conclusion sections.
